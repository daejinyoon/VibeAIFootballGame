# Decisions: 개발자 대상 축구 게임 개발 발표

- Date: 2026-10-27
- Status: Confirmed
- Purpose: 2026-10-28 내부 개발자 발표용 PPT

## D01. 청중과 발표 시간
- **Chosen**: 게임 개발자가 아닌 회사 내부 개발자를 대상으로 10분 발표를 만든다.
- **Rationale**: 게임 규칙 자체보다 개발 과정과 재현 가능한 기획 방법이 청중에게 유용하다.

## D02. 핵심 메시지와 발표 비중
- **Chosen**: “원하는 결과물을 얻으려면 요구사항과 설계 결정을 구체적으로 기획해야 한다”를 중심 메시지로 삼는다. 기획의 변화와 결정 근거를 발표의 중심에 두고, 사용자 정의 스킬은 이를 기록·실행한 방법으로 설명한다.
- **Rationale**: 사용자는 스킬 사용 순서보다 기획의 구체성이 2D에서 목표한 3D 결과물로 가는 데 어떤 역할을 했는지 강조하고 싶어 한다.

## D03. 기획 사례
- **Chosen**: 2026-10-21의 2D 탑다운·6대6·3단계 초기 기획에서 2026-10-22의 실제 3D·4대4·5단계 기획으로 전환한 과정을 핵심 사례로 쓴다. 카메라, 선수 동작, 공 높이·포물선처럼 목표한 표현을 2D로 구현하기 어려웠다는 동기를 설명한다.
- **Rationale**: 사용자가 3D 전환의 가장 큰 계기로 원하는 화면과 움직임의 표현 한계를 선택했다. 변경 전후의 구체적 설계 항목을 보여주면 “상세 기획”이라는 메시지가 추상적 구호로 끝나지 않는다.
- **Evidence**: `.memory/decisions/2026-10-21-football-game.md`, `.memory/decisions/2026-10-22-3d-football-game.md`, 2026-10-21~22 Git 기록.

## D04. 스킬 활용 경로
- **Chosen**: `grill-me → memory-plan → memory-execute`의 사용 순서와 산출물을 보여준다. 대표 산출물은 인터뷰 결정 문서, 전체 계획·Phase·Task 청사진, `.memory/current.md` 포인터, 검증 결과 및 커밋 기록이다. 청중은 AI 코딩 도구는 알지만 사용자 정의 스킬은 낯선 것으로 가정하고 개념을 한 장으로 소개한다.
- **Rationale**: 사용자는 스킬 자체를 어떻게 작성했는지보다 스킬을 사용해 기획을 구현으로 옮긴 경로를 설명하고 싶어 한다.

## D05. 기획 근거의 표현
- **Chosen**: 실제 결정 문서의 짧은 발췌를 사용해 2D와 3D의 카메라·팀 구성·기술 선택을 비교한다. 초기 문서를 현재 게임 사양인 것처럼 표시하지 않고, 각 결정의 날짜와 변경 관계를 명시한다.
- **Rationale**: 개발자 청중에게 실제 문서가 기획의 구체성을 가장 직접적으로 보여준다.

## D06. 기술 이슈 사례
- **Chosen**: 태클할 때 경기 화면이 멈춘 이슈를 대표 기술 사례 하나로 다룬다. 사용자 재현, `MiiPlayerModel.jsx`의 선언되지 않은 `sliding` 참조, `livePlayer.slideSeconds`에서 플래그를 계산한 수정, 자동 테스트·빌드 결과를 간략히 보여준다. 수정 후 Chrome·Edge의 인증된 경기 장시간 테스트와 입력 지연 실측이 남아 있다는 점을 명시한다.
- **Rationale**: 기획에서 작업 청사진, 최소 수정, 검증 범위까지 이어지는 스킬 사용 경로를 하나의 실제 이슈로 설명할 수 있다. 확인되지 않은 전체 탭 멈춤 해결을 단정하지 않는다.
- **Evidence**: `.memory/phases/2026-10-27-football-beta-feedback/P01-game-stability-and-polish/T01-renderer-stability-and-input-latency.md`, commit `1f78f26`.

## D07. 운영 이슈
- **Chosen**: 다른 앱을 향한 Azure 배포 대상 오류를 교훈 중심의 한 장에서 짧게 다룬다. 전용 `ydj-football` 앱과 배포 토큰으로 경로를 고친 사실을 설명하되, 원본 소스가 없어 기존 앱의 원복을 완료했다고 주장하지 않는다. 계정 ID, 토큰, 연결 문자열은 슬라이드에 넣지 않는다.
- **Rationale**: 내부 개발자에게 배포 대상 확인의 중요성을 보여주되 10분 발표의 중심을 기획에서 빼앗지 않는다.
- **Evidence**: `.memory/decisions/2026-10-27-ydj-football-azure-target.md`, commits `9e442ba`, `7ff0d9f`.

## D08. 슬라이드와 시각 자료
- **Chosen**: 실제 게임 화면은 최소화하고, 기획 문서 비교·프로세스 도식·작업 파일·커밋 기록을 주된 시각 자료로 쓴다. 10분에 맞는 간결한 슬라이드로 구성한다.
- **Rationale**: 발표 청중은 게임 개발자가 아니며, 사용자는 게임 플레이보다 개발 과정을 강조하고 싶어 한다.

## D09. 산출물
- **Chosen**: 편집 가능한 PPTX 파일을 만들고 각 슬라이드에 10분 발표용 핵심 멘트와 전환 문장을 발표 메모로 포함한다.
- **Rationale**: 사용자가 다음 날 직접 발표하며, 메모가 시간 관리와 설명을 돕는다.

## Codebase findings and boundaries
- `game/`은 React·JavaScript 앱이고 3D 경기는 React Three Fiber·Three.js로 구현되어 있다. 초기 2D 문서의 일부 규칙은 이후 결정으로 대체되었다.
- `.memory/current.md`의 기존 Desktop Responsive Layout 계획은 Task가 모두 완료되어 있다. 이 발표 작업의 계획 단계에서 새 포인터를 설정할 때 기존 완료 기록을 보존한다.
- 태클 이슈의 코드 수정과 자동 테스트는 기록되어 있지만 수정 후 인증된 브라우저 경기 장시간 검증은 기록되지 않았다. 발표에서 “확인된 렌더 예외 수정”과 “전체 멈춤 현상 해결 검증”을 구분한다.
- 이전 Azure 앱의 원복에는 원본 배포 파일이 필요하며 현재 저장소에 없다. 발표는 이를 완료 사례로 묘사하지 않는다.
